# grill

反复与用户访谈，直到达成共识。将此过程绘制成 **设计树**：每个决策都会衍生出后续的决策。

## 流程

**分轮**处理决策树。**边界** 是指所有前提条件已经确定的决策：即你 *现在* 可以提出的问题，而无需猜测你尚未听到的答案。在一轮中询问整个边界：给每个问题编号并给出你的建议答案。然后等待用户的回复，之后再进行下一轮。

格式如下：

```markdown
❓ **Q1** - **<问题标题>**: <question body, might be multiple paragraphs, including multiple choices>

➡️ <你推荐的答案>
```

用户每回答一轮问题，问题树就会重塑：已确定的答案会将边界向外推移，并解锁依赖于这些答案的问题。重新计算边界，然后进行下一轮提问。如果某个问题的答案依赖于本轮中尚未解决的问题，则该问题属于 *后续* 轮次，而非本轮。

寻找 *事实* 是你的工作，而不是用户的。当一个前沿问题需要从环境（文件系统、工具等）中获取事实时，派出一个子代理去查找；不要向用户询问任何你可以自己查找的信息。不要因此而阻塞：正在进行的探索是一个尚未确定的前提条件，因此只有其下游的问题才需要等待子代理的报告；现在就可以向前沿问题的其他部分提出请求。*决策权* 在用户手中：把每个问题都交给他们，然后等待。

## 保存

引导用户保存文档，当设计树的每个分支都已遍历完毕，没有任何未加假设的内容时，会议即告结束。在用户确认已达成共识之前，请勿采取任何行动。

```markdown
**是否保存文档**

A. docs/grill/grill-<subject>.md (推荐)
B. 不保存留在原地
C. 自定义目录或其他说明
```
