# 合并与变基冲突

已授权的合并、变基、cherry-pick 或其他 Git 操作出现冲突时，使用本流程。
处理方式按操作状态及文件类型选择，不假设所有冲突都能手工合并文本。

## 处理流程

1. 检查操作当前状态、源版本和目标版本、历史及冲突文件。
   保留无关的已暂存、未暂存和未跟踪工作。
2. 按需从代码、提交信息及关联需求确认双方意图。
   存在适用的领域技能或工具时按需使用，不将其安装作为前置要求。
   生成产物、二进制、重命名和删除冲突，应按来源、生成规则及预期结果处理，
   并将工具更改限制在相关范围内。
3. 逐项解决冲突，保留双方兼容的意图及目标分支的契约。
   不引入无关功能或大规模重构。如果已有证据不足以协调双方意图，
   报告需要明确的具体决策，不自行创造行为。不擅自中止用户此前正在进行的操作；
   本次自行启动的操作需要恢复时，在授权范围内选择能保全已有工作的方式。
4. 审阅解决后的差异，确认没有遗留冲突标记；仅暂存本次需要的解决结果，
   并核对本次操作已有的暂存内容。暂存后确认没有未合并的索引条目。
5. 按[验证规则](validation.md)处理受影响检查，在授权范围内继续对应操作。
   如果用户要求处理后供审阅且不提交，则在继续操作前停止。
6. 整个操作序列结束后，核对最终 HEAD 和文件树的验证覆盖，以及剩余工作区状态。
   推送遵循[提交与推送](commit.md)流程。

## 结果报告

报告操作类型、源版本与目标版本、已解决文件，以及尚需明确的决策。
对有实际影响的冲突，说明原因、解决方式及剩余风险。
分别报告复用检查、新执行检查、已分类失败和未验证的验收项。
根据冲突复杂度决定报告细节，不机械填充固定模板。
