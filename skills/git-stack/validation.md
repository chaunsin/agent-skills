# Git 交付验证规则

提交、推送、冲突处理及工作树准备共用本流程。根据操作目标和变更影响建立验证证据，
复用输入未发生变化的检查结果。仓库强制门禁和钩子保留各自的执行方式和时效要求。

## 适用检查的来源

先从用户要求、仓库说明、现有检查入口及 CI 配置确定本次需要验证什么、在哪里执行。
检查可以在本机、容器、远程构建环境或 CI 中完成，不要求 agent 具备某种本地运行时。
纯文档、数据、资源、配置和多语言项目同样适用；按相关组件分别判断，不预设构建或测试命令。
仓库没有某类检查或工具时，不为 Git 操作临时引入一套验证工具。

保存进度、草稿推送、完成修复和正式发布可能有不同的验证要求。
区分影响验收结论的待验证项与实际阻塞操作的强制门禁，不把所有检查都变成每次提交的前置条件。
允许保留未完成工作的操作，仍需如实报告失败或未验证状态，不将其称为验证通过。

## 1. 盘点已有验证证据

安排检查命令前，先利用会话结果、已有日志或 CI 记录，为相关检查简要记录：

| 检查及范围 | 已测试版本或内容 | 环境与目标分支上下文 | 结果及证据 | 决定 |
| --- | --- | --- | --- | --- |
| 具体命令或检查入口及涉及组件 | 提交或文件树，以及相关的已暂存、未暂存、未跟踪输入 | 实际执行环境、相关工具及配置、适用的基线或目标版本 | 通过或失败、结果来源及已知边界 | 复用、缺失或失效，并说明原因 |

将这些记录保留在任务报告或会话中；除非仓库要求，不创建受版本控制的记录文件。
区分实际观察到的命令结果和缺乏证据的“测试通过”陈述。
输入不明确或证据不可用时，该检查仍属于未验证。

## 2. 判断哪些检查仍然适用

将已验证状态与最终计划提交或交付到目标分支的状态比较，检查相关文件及其使用方、
依赖和生成输入、检查配置、工具链、执行环境，以及相关目标分支差异。
仅在项目具有相应机制时检查锁文件、工作区包链接或生成资源等输入。

- 影响某项检查的输入没有变化、验证范围覆盖交付内容，且没有强制时效规则使结果失效时，
  复用通过结果。仅提交哈希不同，不会使相同已测试内容的结果失效。
- 补充缺失的必需检查，以及受输入变化影响的检查。
  仅在影响范围、新失败或仓库规范要求时扩大验证。只改文档时，执行适用的文档检查，
  无需触发无关应用构建；文档本身参与生成或构建时，仍要判断其影响。
- 合并、变基、cherry-pick 或交付到其他分支时，检查实际目标版本和最终文件树。
  比较目标分支的相关内容、接口、依赖、配置和工具链与已验证上下文的差异。
  patch-id 一致只说明补丁相似，不能证明目标上下文兼容或检查通过。
- 与某项检查无关的目标分支变化不必使该检查失效，但要说明原因。
  无法确定相关差异或其影响时，在整合后的目标状态上运行受影响检查；
  仅源分支结果不足以证明目标状态已经通过验证。整合前的评审任务只报告目标兼容性的证据和边界，
  不为获取验证结果而擅自执行合并或变基。
- 冲突处理、钩子改写、生成文件变化或环境修复后，重新判断相关结果是否适用。
  如果没有输入变化或未解决的疑点，不因创建提交、工作树路径变化、推送重试，
  或已经分类的失败而重跑全部检查。

如果没有剩余检查，直接继续交付，不为已完成的检查重新安装依赖或探测工具链。
除非任务要求等待 CI 或其属于强制门禁，否则不反复轮询 CI。

## 3. 运行检查前执行一次环境预检

先确定待执行检查使用的环境和入口，再从仓库约定及实际配置确认前置条件。
对同一环境、同一组相关输入集中预检一次；可批量执行的独立只读探测一起完成，
汇总处理已知阻塞项后，再运行依赖这些条件的检查。
只检查实际需要的条件，不把下表当作每个项目都必须满足的清单。

| 前置条件 | 按实际检查需要确认的内容 |
| --- | --- |
| 执行入口和工具链 | 检查脚本、任务执行器或服务可用，相关编译器、解释器、运行时和检查工具符合项目要求。有版本约束时遵循约束，不假设每个项目都有版本管理器或固定版本文件。 |
| 依赖和构建输入 | 所需依赖、模块、生成文件、资源及外部产物与本次内容一致。项目使用锁文件、缓存或本地链接时，核对其有效性及实际解析位置；无此机制时跳过。 |
| 执行环境和配置 | 实际运行位置、操作系统或目标平台、配置及权限满足检查要求。由容器或远程环境执行的检查，在对应环境确认条件。 |
| 外部设施 | 仅在检查依赖服务、设备、网络、凭据或其他设施时确认可用性。缺少敏感配置时报告名称或用途，不暴露值。 |

仅存在依赖目录或缓存，不能证明输入正确或环境已就绪。
复用其他工作区的产物时，确认其来源、解析路径和适用内容，避免验证了其他版本。
仅在条件缺失或失效时，按项目已有流程补齐；若存在锁定机制，遵循该机制。
不在任务授权范围外顺带升级依赖、改写项目配置、安装系统工具或启动真实环境服务。

保留本次执行环境及相关输入的预检结果。工作区、依赖、工具链或配置变化，
或检查暴露新的前置条件时，只重新检查受影响的部分。
某项前置条件无法在任务范围内修复时，汇总报告已发现的阻塞项，继续独立工作，
并将依赖这些条件的检查标记为未验证。

## 4. 重试前先分类失败

| 分类 | 判断证据 | 处理方式 |
| --- | --- | --- |
| 本次回归 | 错误与本次内容变化或整合有关；错误信息支持该判断，必要时有可比基线通过的证据。 | 需要修复且属于本次任务时，在范围内修复并重跑失败检查及受影响检查。要求该项通过的操作继续阻塞；允许保存未完成工作的操作按其约定处理，并明确标记未完成。 |
| 既有基线失败 | 在工具链和配置可比的相关未修改基线上出现相同失败，或可靠的既有证据证明问题早于本次更改。 | 记录失败检查、基线版本和证据，不扩大为无关修复，也不反复重跑。仓库规范允许时继续范围内工作和交付，仍保留强制门禁。 |
| 环境或工具失败 | 必需的工具、输入、配置或外部设施不满足要求，导致检查无法有效执行。 | 针对已确认原因在授权范围内修复，再重跑受影响检查；没有新证据或环境变化时不反复尝试。无法修复时报告未验证及实际阻塞项，不将其描述为通过或内容回归。 |
| 原因未明 | 证据不足以区分本次回归、基线问题或环境问题。 | 进行范围和次数受控的针对性排查，必要时比较可比基线。仍无法确定时报告不确定性，将依赖该结论的验收或门禁保留为未满足，不将其改称基线问题。 |

需要比较基线时，优先使用已有证据；必要时在可用的隔离工作区或等效执行环境检查失败项，
不重置用户工作树。环境不同的情况下，仅错误文本相同不足以证明是同一基线问题。
同一失败特征及相关上下文只需建立一次基线判断，不在每次提交或推送前重复建立。

钩子失败使用相同分类。强制门禁未满足时，按仓库及宿主要求处理，不因分类而自动跳过。
门禁允许使用已有适用证据时可以复用；要求本次执行而未执行的检查，仍属于未满足。
报告分类、证据、受影响的操作和下一步；只有完成相关修复，或确有依据重试临时故障时，才重复执行命令。
