# 提交与推送

按用户要求创建范围明确的提交、推送已有提交，或同时完成两项操作。
工作区干净只表示没有新的内容可提交，仍需判断是否存在待推送的提交。

## 1. 明确操作范围和目标

先确认任务涉及的工作区、引用和更改范围。以下是有工作树时可按需使用的检查示例，
先查看摘要，再读取相关文件或代码块的完整差异，无需每次输出整个仓库的 diff：

```sh
git status --short --branch
git branch --show-current
git diff --cached --stat
git diff --stat
git ls-files --others --exclude-standard
```

结合用户请求和会话历史，确认本次涉及的文件及已有提交。
仅使用 `git diff HEAD` 会遗漏未跟踪文件，也无法清晰区分暂存边界。
对于预先存在的无关更改，只有在是否纳入尚不明确时才询问；不得重置或擅自纳入。
“不提交”限制提交创建，不自动禁止用户已要求的暂存；“只读审阅”则不修改文件或暂存区。
按用户实际要求准备更改，在未授权的操作之前停止。

没有首个提交时，按新增内容检查暂存区，不对不存在的 HEAD 执行历史比较。
裸仓库或仅处理已有引用的任务，跳过不适用的工作树和暂存步骤。

收到推送请求时，即使工作区干净，也要确认已授权的源引用、远端、目标及操作类型。
结合用户请求、已有配置和会话上下文确定目标，不假设拉取上游就是推送目标。
没有上游或 HEAD 处于分离状态时，也可以向已经明确的目标推送；只有目标仍有歧义时才询问。
源引用可以不是当前 HEAD；记录最终确认的源版本，范围检查、验证、实际推送和结果核对使用同一版本。
创建提交或整合改变源版本时，重新核对受影响的范围和证据，无需仅为推送而切换或创建本地分支。

区分直接更新远端引用与托管服务的审阅入口（如 `refs/for/...`）。
审阅入口按服务语义确认实际基线、待提交范围和接收结果，不将入口名当作普通远端分支。

仅做本地提交时，不将访问远端作为前置要求。需要确认目标最新状态时，
在最终比较和安排验证前更新相关远端引用；优先使用已知仍有效的查询或 fetch 结果。
远端状态变化时只刷新受影响的信息，不盲目执行 pull。
以下比较和状态表适用于直接更新分支；目标分支已存在且本地可比较时，
将 `<target>` 和 `<source>` 分别替换为已确认的目标引用及源版本：

```sh
git rev-list --left-right --count <target>...<source>
git log --oneline <target>..<source>
```

两个计数依次表示仅目标引用拥有、仅源版本拥有的提交数。
除文件差异外，还要检查待推送的提交范围，防止意外发布无关提交。

| 状态 | 后续操作 |
| --- | --- |
| 工作区干净，用户要求普通内容提交 | 报告没有新的更改可提交；用户明确要求空提交等特殊操作时，按该请求处理。 |
| 工作区干净，已授权推送，仅本地存在独有提交 | 应用下方验证规则后，推送已经核对的待交付提交。 |
| 工作区干净，已授权推送，双方引用一致 | 报告目标分支已是最新状态。 |
| 工作区干净，已授权推送，仅目标分支存在独有提交 | 报告没有待推送提交且本地分支落后；不为一次多余的推送而整合分支。 |
| 历史已分叉，或待处理更改必须整合目标分支变化 | 推送前按用户请求和仓库规范检查并整合；出现冲突时使用[冲突处理](conflict.md)流程，整合后重新判断受影响的验证。 |
| 目标分支不存在 | 从预期基线检查待发布提交，仅在已授权的推送范围内创建远端分支。 |

不自动为推送而创建空提交，不因工作区干净就切换分支、合并或变基。
执行必要的整合前，先保护本地更改。

## 2. 使用已有验证结果交付

按照[验证规则](validation.md)选择检查、复用证据和处理失败，
确认验证覆盖本次最终源版本或实际暂存内容。

创建内容提交前检查最终暂存差异，按仓库规则执行适用检查；
`git diff --cached --check` 可用于发现空白错误，但不能代替内容验证。
只暂存本次需要的文件或代码块，确保所报告的验证覆盖实际暂存内容：
包含额外未暂存更改的测试结果，未必能够证明即将提交的内容正确。
如果钩子修改了文件，先审阅这些更改并重新判断受影响的检查，再重试。

## 3. 提交格式

提交信息的格式和语言优先遵循用户要求、仓库约定及相关历史。
没有约定时，使用能准确表达结果的简短主题；需要类型和范围时，可参考以下格式，范围及正文均按需填写：

```text
<type>(<scope>,...): <简短描述>

[可选正文，说明具体更改]

[可选脚注，例如 Closes #123 或 BREAKING CHANGE]
```

常见类型包括 `feat`、`fix`、`docs`、`style`、`refactor`、`ci`、`chore`、`perf`。
描述更改后的具体行为，避免使用“修复 bug”“更新”“添加”“解决冲突”等含糊信息，
也不使用纯标点或数字占位。

## 4. 完成已授权的操作

- 按已授权目的创建提交，包括内容提交，或明确要求的空提交、历史整理等操作。
  提交粒度按用户目标和更改关系确定。核对提交哈希、信息和文件，
  并检查剩余的已暂存、未暂存和未跟踪内容。
- 用户已经授权明确的推送目标时，直接推送。仅提交的请求在报告提交结果后结束；
  只有交付意图存在歧义且完成任务需要推送时，才询问推送授权。
- 推送时明确指定最终确认的源对象和目标，并按操作语义核验结果：
  直接更新引用时，核对该引用指向实际推送的源对象；审阅入口使用服务的接收确认、
  审阅记录或实际持久引用核对源版本，不要求入口本身成为引用或目标分支已经合并。
  如果远端期间发生变化，或推送因非快进被拒绝，先检查新状态并重新判断整合和验证要求，
  不自动改为强制推送。明确要求历史重写的任务，仍按既有授权和远端保护规则处理。
- 推送或网络发生临时失败时，先按对应语义检查是否已经成功。
  结果未明且不能保证安全重试时，报告未确认；其余仅对内容未变、仍有必要且已授权的推送有限重试。
  遵循用户或工具已有重试预算；
  没有约定时，总尝试次数默认最多三次，到限报告失败。
  认证失败和分支保护失败应按具体原因处理，不反复重试或重新跑测试。

报告本地分支和工作树、提交哈希、实际推送目标、复用及新执行的验证，
以及既有基线失败和未完成的检查。不将本地检查描述为 CI 或真实环境验收。
操作受阻时，明确指出受阻的操作及原因。
