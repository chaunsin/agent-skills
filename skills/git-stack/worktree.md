# 工作树

创建新工作区前，优先复用合适的已有隔离环境。
按任务需要和当前能力选择宿主工具或 Git CLI，不要求 agent 提供专用工作树功能。

## 步骤 1：检测已有隔离环境

先确认当前仓库及已有工作区。宿主提供相关信息时可以复用，否则直接查询 Git；以下命令按需使用：

```sh
git rev-parse --git-dir
git rev-parse --git-common-dir
git rev-parse --show-superproject-working-tree
git symbolic-ref --quiet --short HEAD
git worktree list --porcelain
```

比较 Git 目录和公共目录前，按当前执行环境将相对路径解析为可比较的实际路径。
目录不同可用于识别链接工作树；同时核对子模块关系和仓库边界，
不把子模块误判为任务所需的独立工作区。相关选项不受当前 Git 支持时，使用等效仓库信息判断。
子模块应按本次操作所属仓库及父仓库状态决定隔离范围。
分离 HEAD 下分支查询没有结果是正常状态，不视为环境失败。

- 已在合适的链接工作树或平台隔离工作区：复用当前环境，直接进入**步骤 3**，
  不进入步骤 2，也不创建嵌套工作树。
- 其他位置存在合适的工作树：切换执行位置；由宿主管理时按其接口附加或选中，再进入**步骤 3**，
  不重置内容，也不自动重跑初始化。
- 没有合适的隔离环境：仅在用户要求或已授权任务确有需要时创建。
  尊重已有偏好；只有选择会实质影响任务且尚不明确时才询问。
  如果继续使用当前工作区，直接进入**步骤 3**。

确认后续操作的工作区位置及分支或提交引用；远程或虚拟环境使用该环境可访问的位置标识。
HEAD 处于分离状态时，可继续适用操作，只在实际需要本地分支时建立分支。
如果用户明确要求新建工作树，即使已有其他工作区，也可能需要按要求创建。

## 步骤 2：仅在需要时创建隔离工作区

### 2a. 选择创建方式

宿主管理工作区且其工具能满足目标基线、执行位置和隔离要求时，优先遵循宿主管理方式。
没有适用接口时可使用 Git CLI 或其他受支持的方式；只有确实受平台约束时才要求注册或附加。
创建完成后核对实际位置和 Git 状态，进入**步骤 3**。
如果工作区已经存在但后续登记失败，先处理该状态，不直接重复创建。

### 2b. Git CLI 示例与目录选择

优先使用用户指定位置或仓库约定；没有约定时，选择不覆盖已有内容、便于当前环境访问和清理的位置。
不预设固定目录名、分支前缀或操作系统路径。使用已有目录前核对归属及内容，不据此自动重置或删除。

选择仓库内部目录时，确认**实际选中的路径**已被忽略；其他候选目录被忽略，不能证明该路径安全：

```sh
git check-ignore -- "<worktree-path>/"
```

如果选定的仓库内目录未被忽略，添加范围明确的忽略规则并检查差异，或使用获准的仓库外位置。
不为设置工作区顺带创建提交。创建前确认预期基线引用，必要时刷新；
尊重用户或仓库的命名约定，不为创建成功而重置已有分支。

确认目录安全和基线引用后再创建工作区。
创建新分支的示例：

```sh
git worktree add -b "<new-branch>" "<worktree-path>" "<base-ref>"
```

使用已有分支时，先确认该分支没有在其他位置检出，再执行
`git worktree add "<worktree-path>" "<existing-branch>"`。
任务无需新分支时，也可使用 `git worktree add --detach "<worktree-path>" "<base-ref>"`。

后续操作明确指向新工作区，避免命令仍在原目录执行。创建受阻时，报告阻塞项，
仅继续不依赖隔离环境的工作。如果任务要求隔离，不擅自回退到原工作区执行修改。

## 步骤 3：准备并验证选定工作区

按[验证规则](validation.md)准备所选检查的执行环境，新工作树不默认触发依赖安装或完整基线测试。
实际使用本地产物、缓存或依赖链接时，核对其来源和适用内容；
远程或 CI 验证则核对任务使用的源版本。

报告选定工作区及分支、环境就绪情况、复用和新执行的检查，以及尚未解决的阻塞项。
仅对实际观察到且仍适用的结果，声明测试通过。
