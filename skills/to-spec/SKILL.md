# 技术规格生成（To SPEC）

将用户提供的需求、决策和上下文转为可供工程师或智能体实施的技术规格。
从现有架构、工程规范、可维护性、性能、质量和安全等角度，明确实现契约，
补充有依据的领域规则，并澄清影响设计的问题。

本技能以生成或修订 SPEC 为目标。默认按 PRD 文档内容处理输入；
当用户明确提供或指定其他类型的材料时，直接依据对应材料开展设计，不强制补写 PRD。

## 何时使用

- 默认根据 PRD 文档，弥合产品需求与实施落地之间的差距；PRD 可以来自 `/prd` 或其他来源。
- 用户指定根据架构决策、访谈或 QA 文档，梳理实现边界、技术方案与验证方式。
- 方案调整阶段，输入材料中的需求或决策发生变化，需要同步修订 SPEC。
- 在编码开始前验证技术可行性，并记录架构选择与实施契约。
- 多个开发人员或智能体将实现同一功能，需要一份共享的技术规格。

## 步骤 1：确认输入材料

### 1.1 默认输入与获取方式

未指定其他输入类型时，默认输入限定为 PRD 文档内容。可以通过以下方式获取：

```markdown
请提供要转换的 PRD 内容：

A. 文件路径，例如 docs/prd/prd-priority-system.md
B. 可访问的文档链接
C. 直接粘贴 PRD 内容
D. 自动查找：在 docs/prd/ 或项目约定的需求文档目录中查找
```

优先使用用户已提供的材料，不重复索要。自动查找时，如果多个 PRD 对应不同功能且目标不明确，
列出候选文档并让用户选择；不要自行把附近的 ADR、访谈或问答记录纳入输入范围。

如果没有找到 PRD，说明缺少默认输入，请用户提供 PRD 内容或指定其他材料。
用户明确指定非 PRD 输入后，直接进入相应处理流程，不要求先调用 `/prd`。

### 1.2 按输入类型提取信息

输入可以是单份材料，也可以是用户指定的多份材料组合：

| 输入类型 | 重点提取 | 解释时注意 |
| --- | --- | --- |
| PRD 文档 | 目标、范围、用户故事、功能需求、验收标准 | 保留已有需求编号；没有用户故事时不强行补造 |
| 架构决策文档（ADR） | 已选方案、约束、权衡、影响范围 | 区分已接受、提议中、已废弃或被替代的决策 |
| 访谈文档 | 使用场景、痛点、业务流程、异常情况、领域规则 | 保留受访者和上下文，区分观察、建议与已确认需求 |
| QA 问答文档 | 问题、确认答案、排除的方案、未决事项 | 保留问题引用，识别后续修订或撤回的答案 |
| 多份材料组合 | 互补的需求、决策与约束 | 去重但保留来源，显式处理冲突，不按文档类型自动确定优先级 |

### 1.3 来源整理

记录材料路径或链接、相关章节及可用的版本或状态信息，区分已确认内容、建议、假设和未决问题。
沿用已有的需求、决策或问题编号；没有编号时，可以引用章节、问答序号、访谈位置，
或使用明确标注为本规格内部使用的引用编号，不要求先整理成 PRD 用户故事。

## 步骤 2：收集工程上下文（按需）

结合工程上下文补充实际落地所需的信息。此步骤用于核实约束和已有实现，
不会自动将参考资料中的建议提升为需求或扩大用户指定的输入范围。

- **现有架构**：系统结构、模块边界和依赖关系。
- **技术栈**：已使用的语言、框架、依赖库和工程工具。
- **复用模式**：文件组织、公共包、通用方法、组件和错误处理方式。
- **代码规范**：命名约定、代码风格和质量标准。
- **数据库**：现有数据结构、迁移工具和 ORM。
- **接口风格**：REST、GraphQL、gRPC 等约定，以及认证方式和响应格式。
- **测试**：测试框架、现有覆盖方式和验证工具。

收集方式如下：

1. 用户提供的描述、文档、图片、链接及其他可访问资源。
2. 项目架构记录，例如 `docs/architecture/ADR-[number]-[title].md`，用于核实适用的技术约束。
3. 项目指导文件，例如 `AGENTS.md`、`CLAUDE.md`、`README.md`，以及与当前设计相关的代码。
4. 项目知识库和文档目录，例如 `docs/`、`spec/`、`plan/`、`prd/`。
5. 当前环境可用且与设计相关的技能和规则，提取约定、最佳实践与已有案例。
6. 需要核实外部技术细节时，优先使用可用的 Context7 MCP 或 CLI；也可以使用网页检索、文档读取或其他知识库工具，不假定某个工具必然可用。

对收集的信息进行分析并归纳总结，用于后续澄清与决策。
现有代码用于说明当前行为，输入材料可能描述目标行为；两者不一致时应说明差异，不能直接用现状否定改动目标。

## 步骤 3：澄清问题与决策

当输入材料中的问题、矛盾、缺失或歧义会影响范围、行为、技术决策或验收时才提出问题，
一次聚焦一个决策。优先复用材料和当前对话中已经确认的答案，不重复询问。

重点检查以下方面：

- **范围与流程**：需求边界、交互流程和业务逻辑是否完整、一致。
- **数据生命周期**：状态流转、终态和副作用是否闭环。
- **异常与风险**：错误处理、限流、降级、安全和兜底是否足以支撑目标行为。
- **实现可行性**：是否存在技术瓶颈，能否复用或扩展已有接口、页面、组件和模块。
- **材料冲突**：文档之间、文档与截图或原型之间是否矛盾，例如字段数量不同；与代码现状的差异是否属于预期改动。
- **隐含规则**：根据工程上下文补充有依据的约定，例如国际化、支付流水、UI 样式、字段命名和领域规则，避免将惯例猜测成既定要求。

已确认的架构决策和问答结论应作为设计依据；存在冲突或用户要求重新评估时再讨论，
不要将提议中的 ADR、访谈建议或未回答的问题当作已达成共识。

不影响关键设计的缺口可以记录为假设，并注明影响和验证方式。
用户要求先出草案时，将尚未确定的关键决策集中到“未决问题”，标明受影响章节，
不要把依赖这些决策的契约写成已经确定；可以继续处理不依赖答案的部分。

格式可以是单选或多选：

```markdown
**问题：需要明确的设计决策**

- [ ] A：方案说明（推荐，说明理由）
- [ ] B：另一方案及其影响
- [ ] C：自定义说明
```

## 步骤 4：编写技术规格

根据 [SPEC 模板](reference/template.md) 创建文档，按技术主题组织内容，
不要逐段复述原始材料。先说明目标、范围、来源和关键决策，再展开架构、数据、接口、
业务规则、错误处理与验证方式。

将范围内的需求、已确认决策和约束映射到对应章节。没有用户故事或功能需求编号时，
直接使用来源引用；没有现成验收标准时，提出可验证的判定方式并标明待确认内容。

保留模板的主要章节层次，根据改动规模控制详细程度。不涉及的部分简述“不适用”及原因，
不要为凑齐模板虚构接口、数据表或性能指标。生成文档默认使用中文，用户指定其他语言时遵循其要求。

## 步骤 5：保存与修订

优先使用用户指定的路径或修订已有 SPEC；未指定时遵循项目文档约定，
通常保存为 `docs/spec/spec-[feature-name].md`。保存位置存在歧义时再询问：

```markdown
**SPEC 保存在哪里？**

A. docs/spec/spec-[feature-name].md（推荐）
B. docs/spec-[feature-name].md
C. 自定义路径
```

修订时更新受影响章节，以及关联的来源映射、契约和验证方式。
保留未受影响的内容和仍然有效的决策，避免整篇重写造成截断或丢失。

## 步骤 6：自我审查

生成 SPEC 文档后，请以全新的视角审视规范，并对照规范检查：

- [ ] 架构选择是否符合实际业务，是否存在过度设计？
- [ ] 边缘情况和错误场景是否完整，数据与逻辑是否闭环？
- [ ] 改动是否影响已有行为，兼容性要求是否明确？
- [ ] 是否有任何部分需要增加或减少详细程度？
- [ ] 是否满足下面的质量标准？

## 质量标准

SPEC 应通过以下检查：

- [ ] 已确定的契约描述完整、无歧义，尚未确定的内容有明确标记。
- [ ] 范围内的需求、已确认决策和约束都有来源引用及对应的 SPEC 章节，延期或排除的内容有说明。
- [ ] 每个功能需求都对应组件、接口、方法或业务逻辑规则，不强制要求存在 HTTP API。
- [ ] 每个验收标准和技术约束都有测试、测量或审查等验证方式，新增的待确认标准有明确标记。
- [ ] 涉及的接口与数据契约足够具体，可以据此实现；不适用的部分有说明。
- [ ] 错误处理涵盖所有已识别的场景。
- [ ] 执行顺序尊重依赖关系，减少摩擦与冲突。
- [ ] 架构、接口抽象、代码模式、设计选择有理有据，不能过度设计。
- [ ] 避免重复实现，应体现充分利用现有标准库、依赖库、通用库、方法。
- [ ] 确有复用价值时，说明公共能力的提取或适配方式，不为通用化增加无关抽象。
- [ ] 已确认结论、建议、假设和未决问题清晰区分，没有把访谈建议或草案决策视为已批准需求。
- [ ] “待定”或“待办”事项已解决或集中到“未决问题”，并标明影响；受阻部分不能宣称可直接实施。
- [ ] 术语、章节层次、来源引用和详略程度一致，读者无需重组原始材料即可理解方案。

## 边缘情况和回退

| 设想 | 处理 |
| ---------------------------------- | ------------------------------------------ |
| 默认流程没有找到 PRD | 请用户提供 PRD 内容或明确指定其他输入，不自行选择其他类型材料，也不强制先生成 PRD。 |
| 输入内容含糊、不完整或相互矛盾 | 澄清关键问题；未决事项记录在第 11.1 节，非关键假设记录在第 11.3 节。 |
| 输入材料与现有代码不一致 | 说明目标变化和兼容性影响；仍需决策的冲突记录在第 11.1 节。 |
| 功能规模超出单份规格的合理范围 | 按功能或服务边界拆分 SPEC，链接共享契约与依赖。 |
| 没有现有代码库（全新项目） | 使用已有约束和领域背景提出架构方案，跳过代码检查，并标明未经验证的实现假设。 |
| 用户指定的 ADR 只有技术决策 | 说明决策的实现影响，只澄清影响设计的目标或行为缺口，不要求补写完整 PRD。 |
| 用户指定的访谈、QA 或需求材料没有用户故事 | 直接将已确认内容映射到 SPEC，提出验证标准并标明待确认项，不补造用户故事编号。 |
| 用户要求不检查代码库 | 跳过代码检查，使用允许查阅的上下文，并标明关于现有实现的假设未经验证。 |
| 用户指定多份同类或不同类型材料生成一份 SPEC | 合并互补内容、去重并注明来源；保留决策状态，明确处理冲突。 |
| 输入链接无法访问 | 说明缺少的材料，请用户提供可访问的内容，不声称已经读取。 |
| 保存后继续修订 | 在原文基础上更新受影响内容，检查是否遗漏原有章节和决策。 |
| 文档完成但用户未要求实施 | 交付 SPEC 和未决事项，将下一步选择交给用户。 |

## 避免反模式

- **不要复述输入材料。** SPEC 应补充技术契约、决策理由和验证方式，而不是用不同措辞复制原文。
- **不要强制转换为 PRD。** 默认输入为 PRD，但用户指定的 ADR、访谈和 QA 文档可以直接用于生成 SPEC。
- **不要虚构共识。** 建议、未回答的问题、已撤回的答案和被否决的方案不等于已确认需求。
- **不要过度描述简单的操作。** 没有特殊逻辑的 CRUD 操作不需要完整的算法部分。
- **不要脱离实际情况选择技术。** 在推荐新工具之前，务必先了解项目目前使用的技术。
- **不要孤立地进行设计。** 规范必须与现有系统相符——相同的模式、相同的约定、相同的风格。
- **不要让决策含糊不清。** 如果你做出了选择（例如，“向现有表中添加列”），请明确说明并解释原因。
- **不要编写实现代码。** 规范描述的是契约和行为，而不是代码。对于复杂的算法，可以使用伪代码。
- **不要遗漏复杂功能。** 不因规模或长度省略需求，必要时按模块或功能拆分为多份 SPEC。

## 后续处理与流程位置

默认从 PRD 开始；其他输入类型由用户明确提供或指定：

```text
PRD（默认）或 ADR / 访谈 / QA（用户指定）
  → /to-spec → SPEC → 按用户要求拆解任务或实施
```

- **`/prd`**：生成 PRD，是可选的输入来源，不是前置条件。
- **`/to-spec`**：生成或继续修订技术规格，即本技能。
- **`/to-task`**：在技能可用且用户要求时，将 SPEC 拆解为可验证任务。

交付时说明文档位置和仍影响实施的未决事项。后续可继续修订、拆解任务，或根据用户要求进入实施；
不要求清空上下文，也不因文档已保存而自动开始编码。
