# 任务拆解

## 1. 目的与职责

将 PRD、SPEC、Issue、技术方案或自然语言需求，拆解为边界明确、可执行、可验证的任务，
形成可供人、Agent 或 Harness 使用的任务计划。生成内容遵循用户使用的语言，机器字段名和枚举值保持固定。

本技能负责：

- 分析需求，识别业务切片，明确任务边界。
- 定义优先级、依赖关系、验收标准和验证方式。
- 生成结构化任务数据与可读报告，并检查完整性、一致性和可执行性。

本技能不负责：

- 执行具体开发、测试、部署或向任务平台发布工作项。
- Agent 分配、任务调度、并行执行策略。
- 驱动运行状态、循环、重试和恢复。

PRD 和 SPEC 是可选输入，不强制先调用其他技能。仅编写需求、设计技术方案、执行任务清单
或创建定时提醒，不应触发本技能。

开始时读取相关来源、项目约定和必要的现有实现，确认目标、范围及已有计划；
依次完成拆解、依赖定义、检查和交付。缺失或冲突的资料会影响业务决策时先澄清，避免猜测。

## 2. 任务拆解原则

### 2.1 拆工作单元，不拆操作步骤

任务应代表具有明确目标和可验证结果的工作单元，而不是文件、命令或操作步骤。

| 不合理的拆法 | 更合适的工作单元 |
| --- | --- |
| 创建文件、添加函数、执行格式化，各建一个任务 | 实现支付订单创建 API，并验证订单创建行为。 |
| 修改三个页面，各建一个没有业务目标的任务 | 完成用户修改收货地址的交互及验证。 |

文件或组件数量可以影响工作量，但不直接决定任务数量。

### 2.2 垂直切片优先，水平分解为辅

优先按业务价值划分，例如：创建支付订单、确认支付、处理回调、申请退款。
再根据独立交付和协作需要，拆分契约、数据模型、前后端或验证工作。

共享数据库、认证、幂等性等基础能力可以独立成任务，但应说明它支持哪些业务工作，
不要机械地按技术层拆分整个项目。

### 2.3 明确任务边界

每个任务都明确目标、范围、范围外、输入、输出、约束、验收标准和验证方式。
输入应能追溯到实际需求、文档章节、用户决定或现有实现。

- 多个任务之间的 API、数据结构、状态模型或消息协议需要单独确定时，建立协调任务。
- 多个组件需要组合起来验证整体行为时，建立集成任务。
- 必须由人作出决定或提供介入结果时，建立人工任务，说明其具体产物。

### 2.4 控制任务粒度

继续拆分的信号：

- 包含多个可独立交付的目标。
- 不同部分具有独立的实现、验证或审查边界。
- 内部存在需要先确认的协作契约或决策。
- 无法在清晰的上下文和范围内完成。

停止拆分的条件：

- 目标、范围、输入和输出明确。
- 验收标准和验证方式明确。
- 前置条件满足后，可以由一个执行单元完成。
- 无需继续拆分即可产生可验证结果。

小需求可以只有一个任务；没有剩余工作时说明原因，不为凑数创建任务。

### 2.5 处理不确定性和阻碍

关键未知会影响范围、业务行为、架构或验收时先澄清，继续处理不依赖该答案的部分。
非关键问题可记为问题或假设，注明影响的任务；不能把关键决策当作普通假设。

用户要求先出草案时，可将待决事项写成 `human` 任务，并让受影响任务直接或间接依赖它。
后续任务应明确“待该决策确定后实施”，不擅自选定答案；未解决的阻塞性问题须在交付时提示。

## 3. 优先级与依赖关系

### 3.1 优先级

每个任务设置一种优先级：

- **P1**：核心业务、关键基础能力、必要的安全要求或关键阻塞任务。
- **P2**：重要的常规功能或辅助能力。
- **P3**：非关键增强、体验优化或可延后的改进。

优先级表示重要程度，不表示执行顺序。

### 3.2 依赖关系

- `depends_on` 是当前任务的前置任务 ID 列表，也是依赖关系的权威记录。
- `blocks` 为可选字段；需要时从 `depends_on` 推导完整反向关系，不独立维护。
- 依赖 ID 必须存在，不允许自依赖或循环依赖，也不能按任务编号推断前置关系。

依赖应体现实际需要的产物或决定。两个任务没有依赖关系，不等于可以安全并行；
共享文件、资源、环境等冲突由执行方结合实际情况判断。本技能不决定调度策略。

## 4. 任务定义规范

### 4.1 任务类型

| 类型 | 用途 |
| --- | --- |
| `implementation` | 实现具体产物，包括代码、文档、配置或测试资产。 |
| `coordination` | 确认共享契约，解决任务之间的协作边界。 |
| `integration` | 集成多个产物，验证组合后的整体行为。 |
| `human` | 获得人工决策或介入结果。 |

按实际需要选择类型，不要求每份计划都包含全部类型。

### 4.2 基础字段

每个任务至少包含以下字段，普通拆解按此表即可完成：

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `id` | 字符串 | 稳定且唯一的任务标识，相同工作沿用原 ID。 |
| `title` | 字符串 | 简明任务名称。 |
| `type` | 字符串 | 采用上表中的任务类型。 |
| `priority` | 字符串 | `P1`、`P2` 或 `P3`。 |
| `status` | 字符串 | 新任务为 `pending`；已有状态保留。 |
| `goal` | 字符串 | 该任务要达成的目标。 |
| `scope` | 非空字符串数组 | 本任务包含的工作。 |
| `out_of_scope` | 字符串数组 | 明确排除的工作，没有额外排除项时为 `[]`。 |
| `inputs` | 非空字符串数组 | 实际需求来源、上下文和前置产物。 |
| `outputs` | 非空字符串数组 | 预期交付物。 |
| `constraints` | 字符串数组 | 实现和验证约束，没有额外约束时为 `[]`。 |
| `acceptance` | 非空对象数组 | 每项以 `condition` 字符串描述完成条件。 |
| `verification` | 非空对象数组 | 每项以 `method` 字符串说明检查方法。 |
| `depends_on` | 字符串数组 | 前置任务 ID，没有依赖时为 `[]`。 |

### 4.3 验收、验证与证据

- **Acceptance**：什么情况下算完成，例如“订单创建失败时显示错误，且不提示成功”。
- **Verification**：如何检查，例如“模拟接口失败，检查页面反馈”。
- **Evidence**：执行后产生的测试结果、日志或人工确认，由后续执行者记录。

每个验收条件都应有明确的检查方式，不能只写“功能正常”“开发完成”。
按需求覆盖成功、相关失败和兼容性场景；需要凭证、部署环境或人工审核时，在输入或约束中说明。
规划阶段不填写尚未产生的执行证据。

### 4.4 按需扩展

需要自动检查需求覆盖、逐项关联验收，或持续维护多个修订时，再使用
[详细数据格式](references/task-format.md)中的需求映射、验收 ID、计划 ID 和修订字段。
这些扩展不作为普通拆解的必填项。已有消费者有格式要求时，遵循其契约，不能擅自简化旧计划。

## 5. 任务记录持久化

### 5.1 输出位置

遵循用户或项目指定的位置。没有约定时，默认创建：

```text
task-plan/
├── tasks.md
└── tasks.json
```

已有文件属于另一项需求时，改用独立目录，例如 `task-plan/<feature-slug>/`，避免覆盖。
用户只要预览时不写文件；无写权限或保存失败时提供草案，明确哪些产物尚未保存。

### 5.2 tasks.md

供人阅读和审查，至少包含：

- 最终目标、范围和业务切片。
- 任务列表、类型、优先级及依赖。
- 各任务的目标、范围、输入、输出、约束、验收和验证。
- 未解决的问题、假设、排除事项和待人工决策内容。

使用清晰的标题、列表和表格；应能从任务说明追溯到需求来源。

### 5.3 tasks.json

作为机器读取的事实来源。基础顶层字段为 `version`、`project`、`goal`、`tasks`、
`open_questions` 和 `assumptions`；前三个为字符串，后三个为数组。
本技能基础格式使用 `version: "1.0"`，版本号不表示执行进度。

下面是一份完整、无悬空引用的单任务示例：

```json
{
  "version": "1.0",
  "project": "记录导出",
  "goal": "为已有 CSV 导出流程补充明确的失败反馈",
  "tasks": [
    {
      "id": "EXP-001",
      "title": "完善 CSV 导出失败反馈",
      "type": "implementation",
      "priority": "P2",
      "status": "pending",
      "goal": "下载失败时用户能看到错误，不会误以为导出成功",
      "scope": ["处理现有导出流程的失败反馈"],
      "out_of_scope": ["修改导出字段和登录方式"],
      "inputs": ["用户要求：导出失败时显示错误提示", "项目现有导出交互和错误反馈约定"],
      "outputs": ["页面反馈变更及针对性验证"],
      "constraints": ["沿用现有接口和登录流程"],
      "acceptance": [{"condition": "下载失败显示可读错误，且不显示下载成功"}],
      "verification": [{"method": "模拟导出失败，检查错误提示及成功提示互斥"}],
      "depends_on": []
    }
  ],
  "open_questions": [],
  "assumptions": []
}
```

有未决问题时，记录字符串 `id`、`question`，布尔值 `blocking`，以及任务 ID 数组 `affected_tasks`；
阻塞性问题还需用字符串 `decision_task` 关联人工决策任务，并满足第 2.5 节的依赖约束。
假设以字符串 `statement` 和任务 ID 数组 `affected_tasks` 记录。受影响任务均引用已有 ID；
非阻塞的全局问题或假设可使用空数组。

生成后检查 JSON 合法、字段类型正确、ID 唯一、引用存在、依赖无环。
需要脚本校验或完整的决策示例时，查阅[格式与校验说明](references/task-format.md)。

### 5.4 双文件一致性

- 两份文件由同一份拆解结果生成，任务、依赖、验收和未决事项保持一致。
- 存在冲突时，机器读取以 JSON 为准；覆盖 Markdown 前检查其中是否包含用户的新决定。
- 保存后回读两份文件。只有一份写入成功时报告部分完成，不能声称整份计划已交付。

### 5.5 已有记录的保护

生成或更新前，先确认目标位置的计划是否属于同一需求：

- 不存在记录：创建初始计划，新任务状态为 `pending`。
- 未开始且仍是同一工作：可调整任务说明、范围或检查方式，保留身份和已有数据。
- 已有执行状态、证据或结果：保留执行记录；已执行工作的新增范围或验收应建后续任务。
- 带有 `estimate`、`owner` 等规划字段不等于已经执行，不因此冻结整个任务。
- 拆分、替换或撤销已有工作：保留旧快照及旧、新 ID 的对应关系，检查受影响依赖。
- 执行系统正在写入：先保存修订提案，由其既有流程协调应用，避免改写正在变化的记录。

保留消费者扩展字段，不因不认识它们而丢弃。保存前重新检查目标文件，避免覆盖其他写入者的更新。
无法判断是否属于同一需求时，覆盖前澄清；用户已经授权的正常创建或更新无需重复确认。

## 6. 拆解完成标准

交付前逐项检查：

1. 最终目标与范围明确，任务能够追溯到真实需求或已确认的支撑工作。
2. 关键业务需求均已覆盖；排除项有明确依据，没有因实现困难而遗漏。
3. 工作单元边界清晰，没有巨型任务或无价值的过度拆分。
4. 任务 ID 唯一，类型和优先级正确，只有新任务初始化为 `pending`。
5. 每个任务的目标、范围、输入、输出和约束完整。
6. 验收条件具体，每个条件都有可行的验证方式。
7. 必要的协调、集成和人工决策没有隐藏在其他任务中。
8. 依赖真实、完整，无自依赖、循环依赖或无效引用。
9. 阻塞问题已关联决策及受影响任务，假设没有替代关键业务决策。
10. JSON 可解析，Markdown 与 JSON 内容一致；使用了扩展字段时也满足相应约束。
11. 已有执行状态、结果和扩展数据完整保留，没有把新增工作当成已经完成。
12. 按约定交付文件或预览草案，并如实说明保存情况、已做检查及待确认事项。

拆解完成不代表任务已执行；结构校验通过也不代表业务可行性或真实 Harness 集成已验收。
