# 任务数据格式与可选校验

[主文件](../SKILL.md)已包含普通拆解所需的基础字段和示例。
需要需求覆盖映射、验收 ID 关联、修订管理或脚本校验时，再读取本说明。
这些扩展属于同一份 `version: "1.0"` 格式，按需启用，不要求普通计划全部填写。

已有消费者有明确契约时，以该契约为准。不能为了简化输出而删掉旧计划已经采用的字段或改变其类型。
本格式不保证任意 Harness 均可直接读取。

## 1. 基础约定

- 使用 UTF-8 严格 JSON，不含注释、尾随逗号、重复对象键、`NaN` 或无穷值。
- 规范字段的字符串非空且无首尾空白；ID 区分大小写，在其所属集合内唯一。
- 基础顶层字段为 `version`、`project`、`goal`、`tasks`、`open_questions`、`assumptions`。
- 每个任务采用主文件第 4.2 节的字段。`acceptance` 对象包含 `condition`，`verification` 对象包含 `method`。
  不使用 ID 关联时，由审查者确认每条验收均有检查方式。
- `tasks` 可以为空，但须在目标或报告中说明没有剩余工作的原因，不能让脚本通过代替这一判断。
- 数组顺序用于展示，不表示调度顺序；空数组使用 `[]`，不使用 `null`。
- 允许消费者扩展字段。保留原数据，不能因不识别字段而删除，也不能仅凭扩展字段存在就认定任务已执行。

## 2. 可选扩展

### 2.1 计划身份与修订

需要跨修订识别同一计划时，一起提供：

| 字段 | 规则 |
| --- | --- |
| `plan_id` | 非空字符串，同一计划保持稳定。 |
| `revision` | 正整数，首次启用时为 `1`，之后每次保存修订增加一。 |

不使用这两个字段时，仍需根据来源、范围和原任务 ID 确认是否属于同一需求，不能只比较项目名。
已经启用的计划在普通更新中保留这两个字段。

### 2.2 需求映射

需要自动检查列出的需求是否被覆盖时，增加顶层非空 `requirements` 数组，并为每个任务提供
非空、不重复的 `requirement_ids` 字符串数组。

每个需求对象包含：

- `id`：唯一字符串。
- `text`：需求内容字符串。
- `source`：实际来源字符串，例如文档路径及章节、Issue URL 或具体用户请求；已知修订时一并注明。
- `exclusion_reason`：可选字符串，只在明确不实施该需求时填写排除依据。

任务只能引用已有、未排除的需求。每项需求至少由一个任务覆盖，或显式说明排除原因。
支撑任务可以共享需求 ID，并说明它为何服务于该需求。不能为了通过校验而排除困难的工作。

未启用映射时，在任务 `inputs` 中保留来源，由语义审查检查需求覆盖。
即使启用了映射，脚本也只能检查已列出的需求，不能发现原始资料被遗漏的条目。

### 2.3 验收与验证关联

需要自动检查逐项覆盖时，在该任务内同时提供：

- 每条 `acceptance` 的 `id`：任务内唯一字符串；`condition` 保持不变。
- 每条 `verification` 的 `acceptance_ids`：非空且不重复的字符串数组；`method` 保持不变。

只要该任务启用了任意一个关联字段，就必须补齐该任务内的全部关联，并覆盖所有验收条件。
不同任务可以独立选择是否启用；普通更新不得把已有的关联静默删掉。

例如：

```json
{
  "acceptance": [{"id": "AC-1", "condition": "下载失败时不提示成功"}],
  "verification": [{"acceptance_ids": ["AC-1"], "method": "模拟下载失败并检查反馈"}]
}
```

这是任务字段片段，不是完整计划。验证方法描述计划采用的检查，不能冒充实际执行结果。

### 2.4 依赖辅助字段

- `blocks`：可选、不重复的任务 ID 数组；必须是 `depends_on` 的完整反向关系。
- `related_to`：可选、不重复的任务 ID 数组，用于说明后续工作或上下文，不产生执行依赖。

两者只能引用已有任务，不能引用自身。运行状态与前置产物是否就绪的对应关系由消费者定义。

## 3. 问题与假设

问题对象包含 `id`、`question` 字符串，`blocking` 布尔值和不重复的任务 ID 数组 `affected_tasks`。

阻塞问题还需包含字符串 `decision_task`，指向具有具体决策产物的 `human` 任务。
`affected_tasks` 此时不能为空，也不能包含决策任务自身；所列任务须直接或间接依赖该决策任务。
只需列出直接受影响任务，其后继通过依赖继承阻碍。非阻塞问题不填写 `decision_task`。

假设对象包含字符串 `statement` 和不重复的任务 ID 数组 `affected_tasks`。
非阻塞的全局问题或假设允许影响列表为空。所有任务引用均须存在。

未决的阻塞问题使计划保持草案性质。得到答案后先记录来源及相应约束，再移除问题；
这不授权规划者改变执行系统的运行状态。

## 4. 可选的只读校验

脚本使用 Python 3.9+ 标准库。从技能目录运行，或相对本技能根目录解析路径：

```bash
# 基础格式与已启用的扩展；新任务必须为 pending。
python3 scripts/validate_task_plan.py /path/to/tasks.json --new-plan

# 与同一计划的旧快照比较。
python3 scripts/validate_task_plan.py /path/to/tasks.json --previous /path/to/previous-tasks.json

# 消费者以自定义字段记录执行结果时，显式指定该字段；参数可以重复。
python3 scripts/validate_task_plan.py /path/to/tasks.json --previous /path/to/previous-tasks.json --execution-field run_receipt
```

没有 Python 时，用现有工具完成等价检查并说明限制，不为拆解任务强制安装工具。
脚本只读取指定文件，不执行计划内的方法，不访问其路径或 URL，也不改写任务。
退出码：`0` 检查通过；`1` 数据或更新错误；`2` 参数或文件访问错误。

`--new-plan` 检查所有任务均为 `pending`；如果启用了修订字段，则初始修订号为 `1`。
普通校验允许已有消费者自己的状态字符串，不推断所有非 `pending` 状态都意味着成功。

### 4.1 更新保护

`--previous` 校验两份文件，并检查：

- 项目一致；已经启用计划 ID 时 ID 不变、修订号递增一。
- 原任务 ID 全部保留；新增任务为 `pending`；已有状态不被重置。
- 计划和任务顶层的扩展字段原值保留；嵌套扩展仍需语义审查。
- 已启用的需求映射和验收关联不在普通更新中消失。
- 已开始或含执行记录的任务保留定义和关联需求快照；派生的 `blocks` 可以更新。

执行记录的判定使用已有非 `pending` 状态，以及有内容的 `evidence`、`result`、`execution`、
`started_at`、`completed_at` 字段。空的 `null`、字符串、数组或对象占位不代表已执行；
`false`、`0` 等实际结果仍视为记录。

`estimate`、`owner` 等普通扩展字段会保留，但它们的存在不会冻结任务说明。
例如，保留 `estimate: "2h"` 的同时，可以修订尚未执行任务的标题。
自定义执行字段通过 `--execution-field` 指定任务顶层键名；脚本不会自行猜测任意字段的含义。
检查者仍须根据消费者契约确认是否存在其他执行记录。

该检查不判断任务身份在语义上是否改变，也不负责撤销任务或修改消费者扩展值。
拆分、删除或替换原任务时，保留旧快照和 ID 对应关系，按消费者流程另行协调；
不能绕过报错后声称已通过受保护的原地更新。执行方持续写入时，先另存提案。

## 5. 示例与校验范围

[完整 JSON 示例](example-tasks.json)和[对应可读报告](example-tasks.md)展示了全部可选映射，
以及人工决策、实现和集成任务之间的闭合依赖。普通任务使用主文件中的简短示例即可。

脚本验证字段形状、已声明的引用关系及有限的更新保护。
它不检查 Markdown 语义一致性、原始需求是否完整、方案是否可行、决策是否获批，
也不证明任务已执行、产物已保存或真实 Harness 集成已通过。
两份输出仍应来自同一份候选数据，并在交付前检查一致性。
