# 依赖最小化与并行性审查

涉及阶段化拆分、复杂汇聚、集中阻塞、长链、关键路径分析或争议依赖时读取本指南。
[主文件第 3 章](../SKILL.md#3-优先级与依赖关系)定义基本依赖语义；本指南维护详细判定、图审查和示例，不定义调度策略或新的 JSON 字段。

## 1. 逐条确认阻塞条件

先看当前任务实际消费什么，再判断是否需要等待。新计划逐边核对；局部审查或增量更新按主文件第 6.1 节限定范围：

1. **所需结果**：上游哪个明确产物、决定或执行结果是必要输入？
2. **受阻范围**：没有该结果，当前任务哪部分实施或验收无法成立？
3. **已有输入**：是否已有确认且可用的契约、文档或实现，可以直接引用？
4. **等待边界**：能否将受阻部分独立为有意义的交付单元，让其余工作先推进？

在任务的 `inputs` 或 `constraints` 中记录前置 ID、所需结果和原因，例如：

```json
{
  "inputs": ["PAY-001 交付的已确认支付接口契约：请求、响应、错误码和状态转换"],
  "constraints": ["界面与模拟响应须符合该契约；真实支付行为由 PAY-005 集成验证"],
  "depends_on": ["PAY-001"]
}
```

这是字段片段，不是完整计划。未完成的契约只能作为待交付输入，不能声称已经确认。

### 1.1 直接依赖与传递关系

若 A 交付数据定义、B 依赖 A 并交付完整 API、C 只验证 B 的 API 行为，C 通常只依赖 B；
A 已通过 B 形成前置链，无需把所有祖先重复写入 C。

若 C 还要独立核对 A 的数据定义，则保留对 A 的直接依赖并记录用途。
不能仅凭图上存在另一条路径，就自动删掉有独立产物或验收依据的边。
上下文引用写入 `references`、`inputs` 或可选 `related_to`，不因此变成阻塞。

### 1.2 区分信息、产物与执行结果

这些分类帮助判断阻塞条件，不增加类型枚举；同一任务可同时需要多类输入。

| 所需内容 | 依赖处理 |
| --- | --- |
| 信息：业务规则、接口约定、状态定义等 | 已确认且可用时直接引用；关键决定尚未确认时，按主文件第 2.5 节澄清，或在用户要求先出草案时建立人工决策任务。技术协作边界由必要的协调任务确认，只阻塞受影响工作。 |
| 产物：接口 Schema、迁移文件、生成代码等 | 指向真正交付所需产物的任务，不连带等待无关实现；已有产物不重复创建待办任务。 |
| 执行结果：已部署服务、已完成迁移、真实接口行为等 | 需要该结果的任务继续等待；静态契约和模拟响应不能代替真实鉴权、迁移、部署或集成结果。 |

### 1.3 提前交付部分结果

只需要上游部分结果时，先评估能否独立交付、验收，以及减少等待的收益是否值得新增交接。
满足时将产物单独建任务，再同步调整双方范围与依赖；否则保留完整切片及必要依赖。
不引用未定义的阶段 ID，也不假定消费者会在上游仍未完成时解除阻塞。

共享协调任务只包含下游共同需要的前置决定，不能混入某个模块的完整实现。
模拟响应或桩须符合明确契约，局部验收与真实集成门槛分别保留；不能通过假定待决答案提前交付。

## 2. 检查任务图中的等待

先列出必要的直接依赖，再查看它们形成的依赖链和汇聚点。小计划用表格即可，
复杂计划可按需画图；无需为审查安装工具，也不要求计算并发排程。

| 审查信号 | 需要核对的问题 | 合理处理 |
| --- | --- | --- |
| 高入度：一个任务依赖多个上游 | 它是否直接消费每项结果？是否混入上下文、祖先或无关模块？ | 逐边说明必要性；可独立交付的部分再拆分。真实端到端验收可保留多个前置任务。 |
| 高出度：一个任务阻塞很多下游 | 共享前置是否混入某个模块的完整实现或无关决定？ | 提取最小的共享契约或分别确认独立边界；真正共享的前置仍可阻塞多个下游。 |
| 长依赖链 | 是否按编号、技术层次或开发习惯串接？单元验证是否被无关模块阻塞？ | 让实现依赖必要契约，将真实组合验证放到产物齐备之后。 |
| 多模块共同汇聚 | 汇聚任务是整体验收，还是把多个独立目标捆在一起？ | 保留整体验收门槛；独立业务切片不必统一等待全项目完成。 |
| 单个任务有大量未受阻工作 | 是否只有最后联调需要上游，其余部分却一起等待？ | 有独立验收价值时拆出实现、契约或集成任务；无需独立交付的步骤仍留在原任务内。 |
| 共享文件、资源或环境 | 是否存在具体冲突，还是仅为避免可能冲突而增加依赖？ | 记录已知限制；真实资源前置需保留，具体执行协调由执行方负责。 |

入度、出度和链长是排查线索，不设统一的依赖数量上限，不自动剪边。
任务数量少、单条依赖多或存在串行链，都不能单独证明拆解有问题。

缺少可信工期和资源约束时，报告主要依赖链及阻塞原因；不要把节点最多的链直接称为精确关键路径，
也不编造可节省的时间。具备可靠估算时，可按需分析影响整体完成时间的关键路径。

## 3. 契约、实现与集成的示例

### 3.1 消除等待整个实现的问题

假设支付接口契约尚未确认，数据库迁移与 API 实现均属于后端工作，前端可以按确认后的契约使用模拟响应。
以下任务均包含自身必要的局部验证；示例不要求将单元测试一律独立成任务。

不合理的串行链为“契约 → 后端 → 前端 → 管理端 → 集成”。前端无需等待后端全部完成，
管理端也无需等待前端。可调整为：

| 任务 | 直接前置 | 所需结果与验收边界 |
| --- | --- | --- |
| PAY-001：确认共享支付接口契约 | 无 | 交付可供实现和模拟使用的请求、响应、错误码与状态约定；不混入后端完整实现。 |
| PAY-002：交付后端支付 API | PAY-001 | 按契约实现、完成必要迁移及后端验证。 |
| PAY-003：交付用户支付界面 | PAY-001 | 按契约实现并用模拟响应验证交互；真实 API 联调属于 PAY-005。 |
| PAY-004：交付管理端支付查询 | PAY-001 | 独立实现并验证管理端契约交互；不等待用户界面。 |
| PAY-005：验证真实支付全流程 | PAY-002、PAY-003、PAY-004 | 消费三方真实产物，验证完整流程和权限边界。 |

PAY-002、PAY-003、PAY-004 在契约就绪后具备独立推进的条件，具体并发仍需检查共享资源。
PAY-005 的多个前置均有直接用途，应保留；无需再因传递关系重复列入 PAY-001。
已有确认契约时直接引用，PAY-001 可以不存在；已执行的旧任务则遵守记录保护，不能直接删除。

### 3.2 保留真实汇聚与决策门槛

若发布验收必须使用 API、移动端、管理端、迁移验证结果和人工安全批准，
且这些产物分别由不同任务交付，验收任务依赖五项是合理的。不能为了减少入度删掉任何一项，
也不应增加一个没有独立交付价值的“汇总完成”任务来隐藏相同的等待。

若金额精度规则尚待人工确认，依赖该规则的实施继续等待；已明确且与此无关的帮助文档可独立准备。
不能假定金额规则已经确定，也不能将整个项目都挂到该决策上。

对于只有“字段决定 → 完整导出切片 → 真实组合验证”的小计划，这条链可能完全必要。
若前后端不需要分别交付，强行增加契约、桩、界面和测试任务反而增加交接成本。

## 4. 更新、记录与复合审查结论

仅审查时交付意见与限制，不重写任务或要求选择保存位置。用户要求应用修改时再进入更新流程。
新建计划时，明确每项依赖所需结果和任务边界；更新计划时，同时检查受影响前置和后继，
同步调整 `inputs`、`constraints`、范围、验收和验证，按新 `depends_on` 推导 `blocks`。
沿用任务身份和执行记录保护：正在执行的计划先提交修订提案，不能借优化依赖重写已执行事实。
外部系统还须按其记录指南核对原生依赖的维护归属及实际增删结果。

任务自身保留具体依赖原因；索引、外部计划概览或审查意见只汇总本次相关的跨任务结论：

- 调整的关键依赖及理由；没有需要调整的边时说明依据。
- 可独立推进的任务组及其必要输入，真实的集成或发布汇聚门槛。
- 主要依赖链、高入度和高出度节点的保留原因或修正结果。
- 已知资源冲突、待确认的阻塞条件，以及尚不能验证的限制。

不适用的图特征无需列空栏目；没有调整项时简述保留依据。会话交付摘述关键变化并链接记录，不再复制完整说明。
不要求新增计划字段、阶段状态、执行批次或并发数量。
结构校验器无法判断上述依赖是否合理；复合审查必须结合实际需求和产物完成。
