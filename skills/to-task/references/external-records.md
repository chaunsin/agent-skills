# 外部系统记录指南

用户选择 GitHub Issues、GitLab Issues 或明确指定的其他任务系统后，再读取本说明。
记录方式的询问和本地默认行为见[主文件第 5 章](../SKILL.md#5-记录方式与持久化)。
本指南负责保存拆解结果，不负责执行任务或启动任务编排。

## 1. 写入前准备

先完成任务拆解与检查，展示待保存的任务摘要，再根据已选方式核实以下信息：

| 记录方式 | 需要核实的信息 | 可用接入方式 |
| --- | --- | --- |
| GitHub Issues | 实例主机、目标 owner/repo、Issues 是否启用、当前身份是否可读写 | 已连接的工具或 API；也可使用已安装并认证的 `gh` |
| GitLab Issues | 实例主机、完整 namespace/project 或项目 ID、Issues 是否启用、当前身份是否可读写 | 已连接的工具或 API；也可使用已安装并认证的 `glab` |
| 其他任务系统 | 用户指明的系统、目标项目或工作区、记录类型、现有接入方式和写入契约 | 当前环境已有的连接器、MCP、CLI、API 或系统支持的导入入口 |

优先使用能完成任务的现有专用工具。CLI 和 API 参数以当前工具说明、版本及目标实例能力为准，
不因另一个平台有同名字段或命令就套用。多账号、多仓库或多个实例无法唯一确定目标时，先补齐目标信息。

用户选择外部系统及明确目标后，可完成已展示范围内的正常创建或更新，无需再次索取相同授权。
缺少认证、权限或可用接入方式时，保留草案并说明缺失条件；不索取令牌正文，也不擅自安装、
配置或改用其他平台。用户同意改用本地后，才按主文件的本地方式保存。

## 2. 任务与计划记录

### 2.1 单个任务记录

每个任务通常对应一个 Issue 或工作项，正文应让未参与拆解的人也能理解并接手。
采用[主文件第 4 节](../SKILL.md#4-任务定义规范)的完整任务定义；平台没有专用字段时放入正文，
不因字段不足省略验收、验证或约束。

外部记录启用[计划身份与修订](task-format.md#21-计划身份与修订)，使用稳定的 `plan_id` 和任务 `id`
识别同一工作，平台编号作为附加映射。沿用已有值；首次启用时设置 `revision: 1`。
编号由平台返回，不能拿任务顺序、逻辑 ID 或 GitLab 的全局 `id` 猜测项目内的 Issue 编号。

可按以下结构组织正文，语言遵循用户要求：

```markdown
## 计划与任务标识

- 计划 ID：<plan_id>
- 任务内容修订：<最后成功写入本任务内容的计划 revision>
- 任务 ID：<id>
- 类型：<type>
- 优先级：<priority>
- 任务状态：<status>

## 目标与上下文

<计划的最终目标、业务切片、本任务目标，以及可理解的需求背景>

## 范围与范围外

<scope 与 out_of_scope，明确各自边界>

## 输入与输出

<inputs 与 outputs；保留来源引用，并补充接手任务所需的上下文>

## 参考资料

| 资料 | 定位与版本 | 与本任务相关的内容 |
| --- | --- | --- |
| <文档名称及实际链接> | <章节、页码、设计节点及已知版本> | <需求、约束或交互要点摘要；未读取时注明限制> |

## 约束

<constraints；无额外约束时说明无>

## 验收标准

- [ ] <acceptance.condition>

## 验证方式

- <verification.method；说明对应验收项>

## 前置依赖

<depends_on 中各任务的逻辑 ID 与已确认的记录链接；没有依赖时说明无>

## 未决问题与假设

<相关问题、是否阻塞、决策任务及假设；没有时说明无>
```

标题沿用任务 `title`，可加逻辑 ID 方便查找。启用需求映射、验收 ID 或其他消费者扩展时，
通过系统字段或正文保留，不能在发布时丢失。新任务保持 `pending` 语义，原生状态按平台契约映射；
已有状态和执行记录沿用，不把创建成功记为任务完成，也不为匹配模板而重开已关闭的 Issue。

计划级目标、`scope`、`out_of_scope`、未决问题和假设保存在下述计划记录中，并从各任务链接。
它们与任务内同名字段分别保存；未归属单个任务的全局事项不能遗漏。
本地文档引用需附足够的上下文，不能假设平台读者能访问作者机器上的文件。
任务 `references` 逐项映射到“参考资料”。已有可访问的仓库文档、PRD、SPEC 或设计链接时直接引用，
保留章节、节点和版本；只有本地文件时，记录仓库内路径及必要摘要，标明平台读者的访问限制。
不要把本地相对路径直接当成平台链接，不编造外链，也不为建立链接擅自上传原文。

标签、负责人、里程碑、父子关系等元数据按用户要求或已有项目约定设置，并核实目标值。
没有优先级标签时可在正文保留 `P1/P2/P3`，不为此自动新建标签或修改项目配置。
普通关联、父子关系与阻塞依赖含义不同，不能互相替代。

### 2.2 计划修订与发布进度

在所选系统中保留一处可回读的计划记录，优先复用已获授权的计划概览、文档或原生计划对象；
需要新建概览工作项时，提前将其纳入待保存摘要。不要仅为保存进度自动创建本地副本。
该记录保留计划级信息，并记录：

- 稳定的 `plan_id`、最近一次全部保存并核对完成的计划修订；首次发布前记为“尚无完成修订”。
- 当前待发布的目标 `revision` 及候选计划快照，包含本次任务定义、依赖和范围。
  快照可通过所选系统支持的文档或附件保存；引用应指向可回读的确定版本。
- 任务 ID 与实际记录的映射、各任务最后成功写入的内容修订，以及内容和依赖的逐项保存结果。
- 本计划已确认维护的原生依赖关系，包含关系两端的任务／平台标识、方向及接口提供的关系 ID。

`revision` 表示整份候选计划的版本；任务正文中的“任务内容修订”表示该任务最后一次成功写入的版本。
只修改 B 时，无变化的 A 可以保留旧内容修订，计划记录须明确 A 被当前修订复用。
不能只取所有 Issue 中最大的修订号，就认定整份计划已发布完成。

写入任务前先保存目标修订及候选快照，过程中持续记录已确认结果；只有全部任务及依赖按所选表达方式
回读核对后，才推进最近完成修订。部分成功或结果待核实时，保留未完成标记和同一目标修订，
续接不增加修订号、不重建任务。需求再次变化时形成新的候选，保留旧候选的未完成情况及已有记录，
不能将未完成发布当成已完成基线。计划记录自身保存失败或结果不明时，先核实再继续任务写入。

## 3. 保存顺序与依赖

1. **读取并去重。** 读取已有映射和目标系统记录，按计划 ID、任务 ID、来源及范围识别同一工作。
   查找包含已关闭记录，处理分页；不能只凭标题相同就覆盖，也不能只查首批结果就认定不存在。
   读取当前内容、版本和原生关系，准备本次操作的原值、目标值及维护归属，更新时先遵守已有执行记录保护。
2. **先保存前置任务。** 按 `depends_on` 的拓扑顺序创建或更新，取得实际编号或系统 ID 后立即保留映射及可用链接。
   已存在且无变化的任务直接复用。创建顺序仅服务于引用建立，不代表执行顺序或并行调度决定。
3. **保存依赖。** 用实际映射填写正文链接；没有 URL 的系统保留可查询的记录 ID。
   平台及当前接口支持时，按下述差异规则调整原生阻塞关系；不支持时保留明确的文字依赖并说明限制。
4. **回读核对。** 检查任务标识、关键内容、状态和依赖方向，确认写入的是选定目标。
   分开记录工作项保存结果与依赖设置结果，更新计划记录的逐项进度，全部核对后再标记该修订完成。

更新依赖时，比较旧、新 `depends_on` 和平台实际关系：

- 补建目标集合中尚不存在的关系；将已回读确认由本计划建立的关系记入维护记录。
- 对已取消的关系，只移除有记录证明由本计划维护、或用户明确授权移除的关系。
  已存在的关系不能仅因本次需要它就被自动纳入维护；人工关系和归属不明的关系先保留。
- 若原生关系与新计划冲突，说明多出或缺少哪些边、维护归属及影响，再按已有授权处理；
  无法确定归属或缺少删除权限时，标记依赖未完成，不通过重写正文掩盖旧阻塞仍然存在。
- 回读本计划维护的最终依赖集合，而不只检查新增边。其他人工关系单独列出，避免误删。

例如 B 从依赖 A 改为依赖 C，应建立 C→B，并移除本计划维护的 A→B；如 A→B 属于人工关系，
先保留并报告冲突。仅写上“依赖 C”不代表平台的旧阻塞已解除。
没有原生依赖能力时明确报告只保存了文字依赖，不能声称平台会自动阻止执行。

`depends_on` 始终是逻辑依赖的依据。例如 B 的 `depends_on` 包含 A，表示“B 被 A 阻塞”，
对应“A 阻塞 B”；原生关系的 API 参数方向需按该平台契约核实。父子关系不自动产生阻塞边。
前置任务创建失败或结果不明时，暂停受影响任务的发布；不虚构编号，也不丢掉依赖后继续发布。

## 4. GitHub Issues

使用明确的主机和仓库作为每次操作的目标，避免 CLI 根据当前目录误选仓库。
需要 CLI 时先检查 `gh issue create --help` 及当前认证状态。最小创建示例：

```bash
gh issue create \
  --repo "$issue_repo" \
  --title "$issue_title" \
  --body-file "$issue_body_file"
```

`issue_repo` 是已核实的 `[HOST/]OWNER/REPO`；其余变量分别为任务标题与已准备好的 UTF-8 正文文件。
正文优先通过工具的结构化参数或文件传入，保留真实换行，不将 Markdown 拼接为可执行的 shell 文本。

原生阻塞关系和子 Issue 通过当前工具确实支持的参数或 API 设置；不能照搬参考资料中的
`--blocked-by`、`--parent` 等参数而不检查实际支持情况。记录返回的 Issue 编号和 URL，
再回读内容与关系。添加父 Issue 需有明确的目标及关联依据，不能只因需求来自某个 Issue 就自动挂靠。

命令参数参考：[GitHub CLI issue create](https://cli.github.com/manual/gh_issue_create)。

## 5. GitLab Issues

显式指定目标实例和完整项目路径，保留子组层级；自托管实例不能默认成 `gitlab.com`。
读取平台返回的项目内 `iid` 和 `web_url`，同时按接口需要保留全局 `id`，三者不可混用。

需要 CLI 时先检查 `glab issue create --help` 及当前认证状态。支持正文文件参数时可使用：

```bash
glab issue create \
  --repo "$issue_project_url" \
  --title "$issue_title" \
  --description-file "$issue_body_file" \
  --yes
```

`issue_project_url` 是包含目标实例主机及完整项目路径的已核实 URL；标题和正文文件含义同上。
示例用于用户已选定目标后的保存，`--yes` 仅跳过 CLI 自身的提交提示，不能代替主文件的记录方式询问。
旧版工具不支持正文文件参数时，改用可用工具的结构化参数或 API，不以不安全的 shell 拼接替代。

核实目标实例、许可及接口是否支持所需的 Issue links 和阻塞类型，明确区分
`relates_to`、`blocks` 与 `is_blocked_by` 的语义及方向。普通关联不能冒充阻塞关系；
不可用时按第 3 节保留文字依赖并说明限制。

命令参数参考：[GitLab CLI issue create](https://docs.gitlab.com/cli/issue/create/)。

## 6. 用户指定的其他任务系统

只接入用户明确指出且当前环境已有可用入口的系统。先读取其现有文档或工具定义，确认：

- 目标项目或工作区、记录类型，以及必填字段和稳定标识。
- 如何保存任务定义、优先级、待办状态、验收标准、验证方式及依赖。
- 如何查询、创建、更新及回读记录，是否支持只保存草案或待办项。
- 写入是否会触发自动派发、执行或修改其他运行状态。

字段映射遵循实际契约；缺少必要值时询问，不发明 API、命令或任务状态。
没有原生依赖字段时保留可追溯的文字关系。若系统只能导入文件，先生成符合契约的导入草案，
只有取得并回读系统内记录后才能报告“已记录到系统”；生成导入文件本身不等于导入成功。

如果创建记录必然触发执行且无法关闭，停止该写入，说明副作用并交付草案，
由用户决定后续执行方式。本技能不启动调度器、派发 Agent 或运行任务中的命令。

## 7. 更新、失败与续接

更新遵循[已有记录保护](../SKILL.md#57-已有记录的保护)。写入前重新读取目标记录，
有版本或条件更新能力时使用它；检测到并发修改时先合并或提交修订提案，不覆盖用户的新内容。
新任务可使用完整模板，更新时只修改本次涉及的规划内容，并保留已有执行状态、结果与扩展字段。
内容更新和依赖更新分别记录原值、目标值及可用版本，供超时后判断是否已经应用。

| 情况 | 处理方式 |
| --- | --- |
| 认证失败、无权限或目标不可用 | 停止相应写入，说明原因，提供草案并询问是否改用本地 |
| 部分任务保存成功 | 在计划记录中保留映射和逐项结果；续接同一候选修订，先回读后只处理未完成操作 |
| 创建超时或响应丢失 | 按稳定身份查找并核对内容；已创建则复用，只有能确认尚未创建时才重试 |
| 内容更新超时或响应丢失 | 回读本次目标字段；已与候选一致则记为成功，仍为原值且没有并发变化时才重试本次更新 |
| 依赖增删超时或响应丢失 | 回读实际关系集合；目标差异已应用则记为成功，否则仅重试确认未应用且仍获授权的增删 |
| 查询不足或发现并发变化 | 保留待核实或冲突状态；补充查询、合并修订或提交提案，不凭记录存在、旧响应或超时本身盲目重试 |
| 记录创建成功但依赖设置失败 | 保留记录并报告依赖未完成；可补充文字链接，但不冒充原生阻塞关系 |
| 记录已由执行方修改 | 保留现状与旧快照，按既有流程提交修订提案，不重置状态 |

不通过删除已创建 Issue 来自动回滚，也不静默切换记录方式。
一次有依据的重试后仍失败或无法核实时，停止该操作并报告当前结果，保留后续续接所需的信息。
最终报告包含记录方式、具体目标、任务 ID、实际编号或系统 ID、URL（如有）、保存结果及依赖结果。
同时给出计划记录入口、最近完成修订和未完成的目标修订；进度标记仅表示记录保存情况，不表示任务已执行。
文字依赖、草案、失败和结果待核实项均明确列出；只有成功保存且完成回读的内容才作为已验证结果。
