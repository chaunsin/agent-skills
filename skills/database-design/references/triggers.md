# 触发器使用与编写规范

## 1. 使用原则

- **默认不使用触发器承载常规业务逻辑**。优先选择数据库约束、原子 SQL、显式事务和应用层业务逻辑。
- 仅在必须由数据库统一保障、且多个写入入口都无法可靠遵守时，评估使用触发器；须经数据库/架构评审并说明收益与替代方案。
- 跨服务副作用（HTTP/RPC、消息通知、支付、邮件等）不得直接在触发器中执行；采用 Outbox、CDC 或事务提交后的可靠消息机制。
- 高并发核心表、热点行和关键交易链路默认避免复杂触发器；必要时验证锁竞争、事务耗时、吞吐量和死锁风险。

## 2. 编写约束

1. **短小、简单、单一职责**：触发器只做必要的数据库内操作，不承载完整业务流程或状态机。
2. 禁止或严格限制游标、全表扫描、大范围批量修改、递归触发和多层触发链；避免触发器再次修改其触发表导致循环或难以预测的行为。
3. `UPDATE` 触发器应判断目标字段是否实际变化，避免无意义写入；逻辑必须可重复执行，避免重复累计、重复插入或重复产生副作用。
4. 触发器中的 SQL 必须使用明确条件、索引和受控写入范围；不得假定触发器执行顺序、影响行数或并发行为在不同数据库间一致。
5. 不要在触发器中隐藏关键业务规则。若业务正确性依赖触发器，必须在文档、测试和运维流程中显式说明。
6. `updated_at` 由应用还是触发器维护应统一选定，避免两处同时更新；需定义精度、时区和更新语义。

## 3. 数据库差异与交付

- 编写前核实目标数据库及版本的触发器粒度、时机（BEFORE/AFTER/INSTEAD OF）、行级/语句级、事务语义、递归限制、级联行为和错误处理方式。不可将 MySQL、PostgreSQL、SQL Server 等语法及行为视为通用。
- MySQL 常见触发器为行级；PostgreSQL 支持行级和语句级触发器；SQL Server 触发器按语句触发，需正确处理多行 `inserted`/`deleted` 集合，不能假设单行。
- 触发器应纳入版本化迁移脚本、代码审查、权限控制、测试、部署与回滚计划。测试至少覆盖单行/多行写入（若适用）、字段未变化、异常回滚、并发、递归/级联及删除/更新行为。
- 维护触发器清单：名称、所属表、事件、时机、职责、依赖对象、负责人和回滚方式；监控其引起的异常、锁等待、死锁和事务耗时。
