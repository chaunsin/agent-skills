# 主键与 ID 生成策略

本文件用于选择主键类型、单库自增和分布式 ID。主键策略应在设计早期确定，避免后期修改所有关联字段和索引。

## 1. 基本原则

1. 主键必须唯一、非空、稳定，并尽量短。
2. 常规业务实体表默认使用数值型代理主键；默认优先评估 64 位整数（`BIGINT`）。
3. 不要把可变业务属性（手机号、邮箱、名称、订单状态等）作为主键。
4. 主键生成策略与数据分片路由策略是两个独立决策：主键负责唯一标识，分片键负责定位数据。二者可以相同，但不得默认等同。
5. 主键及全部关联字段必须使用兼容的数据类型、精度和有符号属性。
6. 分布式 ID 的唯一性来自生成算法和部署约束，数据库仍应通过 PRIMARY KEY/UNIQUE 约束兜底。

## 2. 单数据库、单写入节点

默认采用数据库生成的数值型自增主键：

- MySQL：常规业务可默认评估 `BIGINT UNSIGNED AUTO_INCREMENT`。
- PostgreSQL：默认评估 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 或按写入控制要求使用 `GENERATED ALWAYS AS IDENTITY`。
- 其他数据库按其原生 identity/sequence 机制适配。

使用 `AUTO_INCREMENT`、Identity 或 Sequence 时，必须理解序列可能因回滚、缓存、故障或手工写入而出现间隙。**自增只表示由数据库生成递增值，不保证数值连续无缺口。** 不得使用主键 ID 推导订单数量、业务顺序或业务时间。

如果项目需要同时兼容 MySQL 和 PostgreSQL，逻辑模型宜约定为正数范围内的有符号 `BIGINT`，物理 DDL 再做适配：MySQL 的 `BIGINT UNSIGNED` 超出 PostgreSQL `BIGINT` 可表示范围的值无法直接兼容。若确认只部署 MySQL，可使用 UNSIGNED 的额外正数范围，但应评估其算术语义及跨库迁移影响。

## 3. 分库分表或多节点写入

当多个数据库节点、服务实例或离线客户端需要独立生成 ID 时，评估全局唯一 ID 方案。优先考虑整数型趋势递增 ID 或时间有序 UUID：

### Snowflake 类 ID

适合需要 64 位整数、分布式本地生成和较小索引键宽度的场景。典型实现由时间戳、节点/工作进程标识和序列号等部分组成。

必须处理：

- worker/node ID 的唯一分配、租约和回收，防止节点标识冲突。
- 时钟回拨、时钟漂移、同一时间粒度内的并发序列耗尽。
- 时间戳位数、纪元、序列位数和节点位数的容量规划。
- 服务重启、容器扩缩容及多地域部署下的唯一性。
- 生成失败、等待或降级策略。

Snowflake 通常是**全局唯一且趋势递增/时间有序**，不是严格连续自增，也不保证多个节点间严格按生成时刻全局单调排序。不同节点时钟和并发会影响观察到的顺序。

如果目标数据库使用有符号 `BIGINT`（例如 PostgreSQL，或 MySQL/PostgreSQL 共用逻辑模型），必须确保 Snowflake 生成值始终处于 `0` 至 `2^63-1` 的可表示范围；不得把可能设置最高符号位的任意 `uint64` 直接映射到 PostgreSQL `BIGINT`。

### UUIDv7

适合分布式生成、跨系统传递和 128 位 UUID 生态。UUIDv7 将时间信息放在高位，整体具有时间排序特征；同一时间粒度内仍含有子毫秒/随机等部分，不应视为严格连续整数。

必须评估：

- 应用语言、数据库驱动和 ORM 对 UUID 的支持。
- MySQL 的实际存储格式（例如二进制 16 字节或文本格式）及比较/索引行为。
- PostgreSQL 的原生 UUID 支持及目标版本是否提供内置 UUIDv7 生成函数。
- 生成器的并发、时钟和排序特征。

PostgreSQL 18 文档提供 `uuidv7()`；较早版本不能假设存在该内置函数，可以由应用生成或采用经验证的兼容方案。

### 其他有序 ID

可评估 ULID、时间有序 UUID 或项目已有的 ID 服务，但必须检查其唯一性机制、同毫秒排序能力、时钟依赖、字典序特性、位数和数据库存储成本。不得仅凭“有序”名称就认定满足所有排序要求。

## 4. 有序 ID 与索引局部性

1. 对 B-Tree 主键索引而言，随机 UUIDv4 等随机键通常会分散写入位置，可能降低缓存和页局部性，并增加索引页分裂及维护成本。
2. 自增整数、Snowflake 和 UUIDv7 等趋势递增/时间有序键通常更有利于保持插入局部性，但不保证完全消除页分裂或在所有负载下更快。
3. 递增键在极高并发写入下也可能形成索引右端热点/争用，必须结合数据库引擎、写入并发和实测评估。
4. MySQL InnoDB 通常以主键作为聚簇索引；二级索引记录会携带主键值，因此过长的主键会放大二级索引空间与写入成本。优先避免不必要的宽主键。
5. PostgreSQL 的普通表默认不因主键而自动按主键物理聚簇；B-Tree 主键索引仍受随机/有序键插入行为影响，但不能把 InnoDB 的聚簇表结论直接套用到 PostgreSQL heap。
6. “有序 ID 可改善索引局部性”是设计倾向，不是性能承诺。应通过目标数据库、真实数据量和实际写入模式验证。

## 5. 不允许的误用

- 不得声称 Snowflake 或 UUIDv7 能生成严格连续、无间隔的 ID。
- 不得使用 ID 连续性判断业务记录是否缺失。
- 不得把 Snowflake 的生成时间直接当作业务发生时间；业务时间应单独存储。
- 不得认为 Snowflake 主键天然就是合适的分片键。
- 不得为了分库分表机械选择 UUID；应结合键宽度、生成服务、数据库引擎、跨库合并和路由需求选型。
- 不得忽略唯一约束、节点标识冲突、时钟回拨或 ID 溢出风险。

## 6. 选型速查

| 场景 | 默认评估方向 | 重点风险 |
|---|---|---|
| 单库、单写入节点 | MySQL `BIGINT UNSIGNED AUTO_INCREMENT`；PostgreSQL `BIGINT IDENTITY` | 溢出、序列管理、ID 有间隙 |
| MySQL/PostgreSQL 双数据库兼容 | 正数范围内的有符号 `BIGINT` 逻辑约定 | MySQL UNSIGNED 范围无法完整映射 PostgreSQL BIGINT |
| 多节点写入，偏好整数键 | Snowflake 类 64 位 ID | worker 分配、时钟回拨、序列容量 |
| 分布式生成，接受 UUID | UUIDv7 | 128 位键宽、版本支持、生成器顺序 |
| 安全不可预测的外部标识 | 内部数值主键 + 独立外部随机标识 | 不要把可枚举 ID 暴露等同于授权控制 |

## 7. 关联表与迁移

- 主表和所有引用字段必须保持类型一致。
- 若主键从自增切换为分布式 ID，应先评估全量关联字段、外键、索引、缓存键、消息事件、API 合约和历史数据迁移。
- 纯关联表可用联合主键，不必机械增加 surrogate ID；但需要独立引用或具有自身属性时，可使用独立主键加联合唯一约束。
- 新 ID 方案上线前，应验证并发生成、节点重启、时钟异常、故障恢复和多环境冲突。
