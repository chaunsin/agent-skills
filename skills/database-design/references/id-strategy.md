# Primary Keys and ID Strategy

Choose IDs early to avoid changing references and indexes later. Keys must be unique, non-null, stable, and reasonably short; do not use mutable business attributes as primary keys. For ordinary entities evaluate a 64-bit numeric surrogate key. Ensure all references have compatible types, precision, and signedness, and retain database PRIMARY KEY or UNIQUE constraints even for distributed IDs. Primary keys identify rows; shard keys route them and need not be the same.

## Single writer

Evaluate MySQL `BIGINT UNSIGNED AUTO_INCREMENT` or PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY` (or `ALWAYS` when explicit overrides should be restricted). Adapt to other databases' native mechanisms. Identity and sequences can have gaps from rollback, caching, failure, or manual writes. Do not infer record counts, business order, or event time from IDs.

For MySQL/PostgreSQL portability, use the positive signed `BIGINT` range in the logical model; MySQL unsigned values above PostgreSQL's signed limit cannot be mapped directly. If MySQL alone is confirmed, evaluate unsigned arithmetic and future migration consequences.

## Distributed generation

When independent nodes, services, or offline clients must generate IDs, assess ordered integers, UUIDv7, ULID, or an existing ID service against uniqueness, ordering, storage, routing, and operational requirements.

Snowflake-style IDs offer compact distributed integer keys. Define unique worker allocation, leases and reuse; clock rollback and drift handling; sequence exhaustion; epoch and bit capacity; restart, scaling and multi-region behavior; and failure, waiting or fallback policy. They are generally time-ordered, not gapless or strictly globally monotonic across nodes. For signed `BIGINT`, ensure values remain within 0 to `2^63-1`; arbitrary `uint64` values may overflow.

UUIDv7 is a 128-bit time-ordered UUID, not a gapless integer. Assess generator concurrency, clock and ordering properties, language/driver/ORM support, MySQL binary versus text storage and index behavior, and PostgreSQL version support. PostgreSQL 18 documents `uuidv7()`; do not assume earlier versions provide it. Other ordered IDs require the same scrutiny of uniqueness, same-millisecond ordering, lexicographic behavior, clocks, width, and storage.

Ordered keys often improve B-tree insertion locality relative to random UUIDv4, but can cause right-edge contention under heavy writes and do not guarantee better performance. InnoDB clusters rows by primary key and carries that key in secondary indexes, so wide keys increase costs. PostgreSQL heap tables are not automatically physically clustered by primary key. Measure on the actual engine and workload.

Do not use IDs as proof of missing records or as business timestamps, assume a Snowflake key is a suitable shard key, or select UUID mechanically for sharding. For unpredictable external identifiers, evaluate a separate random public ID; unguessability does not replace authorization.

## Changes and associations

Pure join tables can use a composite key; use a separate key plus composite uniqueness when independent references or attributes justify it. Before changing IDs, assess all references, foreign keys, indexes, caches, events, APIs, and historical data. Validate concurrency, restarts, clock anomalies, recovery, overflow, and cross-environment collisions.
