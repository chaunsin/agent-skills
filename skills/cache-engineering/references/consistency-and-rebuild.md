# 缓存一致性与重建细节

按任务读取相关章节；仅做普通键命名或 TTL 调整时无需加载本文件。这里的增强机制均需与业务容忍窗口和现有设施匹配。

## 一、旧数据回填与副本延迟

提交后删除仍可能出现以下时序：

```text
读请求 A：缓存未命中 → 读到数据库旧值 v1 → 暂停
写请求 B：提交新值 v2 → 删除缓存
读请求 A：恢复 → 将 v1 回填缓存
```

后续即使使用 `SET NX`，也可能把 v1 写入已删除的键。另一个来源是回源到滞后副本；二次删除后仍可再次读到旧值。

先确认旧值是否可接受、影响窗口及回源数据源，再选择双删或版本协议；严格读取可绕过缓存，并使用满足新鲜度要求的主库或一致性读机制。提交前删除还会让读请求在事务未提交时重新填入旧数据，因此失效应发生在成功提交之后。

## 二、延迟双删

本技能中的双删指：**提交数据库事务 → 删除 → 延迟 → 再删除**。它覆盖部分在第一次删除后才完成的旧请求回填，只降低竞争概率，不保证强一致。

- 根据回源查询、调度暂停、网络和回填的端到端尾延迟评估延迟，参考 P95/P99、业务窗口及副本延迟，保留余量；不能仅凭平均值或照搬固定毫秒数。
- 延迟应可配置，随负载和环境变化复核；不要求为此建设实时自适应调参系统。没有观测数据时标注暂定值并安排测量，不编造分位数。
- 需要可靠执行时，复用持久任务或调度设施，考虑重启、丢任务、有界重试、幂等和积压告警；进程内 `sleep` 或定时器不能单独承担可靠补偿。
- 晚于二次删除的回填、持续读取滞后副本，以及提交后任务尚未登记就崩溃，仍可能留下旧值。要求不丢失时考虑下一节的传播机制。

## 三、可靠传播：Outbox 与 CDC

| 机制 | 关键前提 | 必须处理 |
| --- | --- | --- |
| 事务 Outbox | 业务变更和事件记录处于同一数据库事务 | 提交后的投递、重复投递、事件保留与积压恢复 |
| CDC / Binlog / 事务日志 | 捕获所有相关提交和写入入口 | 消费位点、日志保留、延迟、断点恢复及漏数后的重建 |

消费者要支持幂等、重试、死信或等效补偿；不假定天然恰好一次投递。重复删除通常安全，但乱序主动更新可能把缓存倒退到旧版本；采用主动更新时需顺序或版本保护。

可靠投递解决失效事件丢失，不自动消除传播延迟、滞后副本和旧读回填。先证明所需新鲜度可满足，再评估开发、部署、监控和恢复成本，不因存在高并发就要求新增队列或 CDC。

## 四、版本控制与 CAS

CAS（比较并交换）需要原子地比较版本并决定是否写入，不能用客户端先 `GET` 比较、再普通 `SET` 代替。

- 数据与版本应来自同一个权威快照；版本由权威系统按实体单调推进，不能依赖多机未同步时钟。
- 只比较“当前缓存里的版本”不够：删除、淘汰或过期后键为空，旧请求可能重新写入。需要可证明有效的版本水位、失效墓碑或等效协调协议，明确更新顺序、保存期限及水位丢失时的处理。
- 若水位也在异步传播，传播到达前仍有竞争窗口；本地缓存也必须参与协议。不能凭“加一个版本字段”宣称解决一致性。
- Redis 脚本或事务只保证其覆盖范围内的原子性，不能原子提交外部数据库；涉及多个键时检查 Cluster 同槽约束。

版本方案难以证明或成本超出收益时，选用业务允许的短期旧值策略，或对关键读取绕过缓存。

## 五、热点重建与分布式锁

请求合并优先限制同一键的并发回源，并限制等待者数量与等待时间；进程内合并不能合并其他实例的请求。

需要跨实例协调时：

1. 原子获取带唯一持有者令牌和租约 TTL 的锁，避免“加锁”和“设过期”分开执行。Redis 可用 `SET lock-key token NX PX lease-ms`，参数依据耗时预算确定。
2. 获锁后再次检查缓存，避免等待期间其他请求已完成重建却仍重复回源。
3. 设置回源截止时间；租约过期或续约失败后，旧持有者仍可能运行，不能把带 TTL 的锁当作永久互斥或业务正确性的唯一保障。需要阻止旧持有者写入时，使用受写入端校验的隔离令牌或完整版本协议。
4. 原子比较令牌并释放锁，例如使用受目标版本支持的条件删除或 Lua；先 `GET` 核对再 `DEL` 仍有竞争，直接删除可能释放新持有者的锁。
5. 获取失败或锁服务异常时，有界等待后重读、受控回源、降级或快速失败；允许陈旧读取时才能返回旧值。

采用逻辑过期时，由受控后台任务刷新，保留硬期限、失败告警和并发上限；预热也要分批限速，避免把击穿转移到启动或任务执行时。

## 六、空值缓存与布隆过滤器

- 空值标记要区分真实不存在、缓存未命中、数据库失败和无权访问；权限导致的空结果不能跨用户共享。新建数据后失效对应负缓存，必要时处理旧空查询晚回填。
- 布隆过滤器对**已成功加入的元素**不产生假阴性，但可能把不存在的元素判为“可能存在”；“可能存在”仍需正常查询，不可作为存在性或权限证明。
- 业务新增数据尚未同步到过滤器、过滤器重建不完整或数据丢失时，“不存在”只代表不在当前过滤器中，不能据此拒绝真实数据。只有覆盖范围与同步协议可保证时，才使用负判定拦截；否则回退到受保护的查询路径。
- 标准布隆过滤器不支持直接删除；按需重建或选择支持删除的数据结构，说明额外成本。评估容量、误判率、初始化、同步顺序和重建切换，不能为普通小规模查询默认增加过滤器。

## 七、多级与本地缓存失效

多级缓存要分别定义每层键、容量、TTL、新鲜度及失效顺序。L2 已删除时，某个进程的 L1 仍可能继续命中；进程内锁也不能协调所有实例。

按需求选择短 TTL、版本校验或失效广播。广播、订阅或客户端跟踪需要处理断线、重连和漏通知：可清除受影响本地缓存或重新同步。不能把非持久通知当作可靠队列；清理后重建还要防止旧的在途请求再次填入。
